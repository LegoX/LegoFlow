title: Getting Started
---

This page gets Tracer from verified tasks to agent trajectories. The path is:
fill `config.yaml`, run setup, check the block, launch rollouts, then open the
dashboard.

You can read it as a concrete walkthrough: follow the example config snippets
and commands in order, and you will see how a Tracer run is put together.

## Prerequisites

Before starting, make sure these are available:

- Claude Code with the Tracer plugin loaded.
- Docker, used by Harbor to run task containers.
- `uv` and Python, used to build the Harbor, LiteLLM, and conversion envs.
- An OpenAI-compatible LLM endpoint and API key.
- A task source, usually Curator's `artifacts/merged_swe_tasks/` output.
- Optional Cloudflare credentials, only needed if you want to publish the dashboard.

If the Tracer slash commands are not visible in Claude Code, see
[Q&A](/docs/qa#i-am-in-the-repository-root-but-cannot-find-the-plugin-skills).

## Setup

Most Tracer issues come from a mismatch between the task source, model endpoint,
agent scaffold, and conversion settings. Once `config.yaml` is aligned, the
skills handle the environment and launch details.

For a first run, leave `meta_info` and `runtime_info.output` alone. Fill the
`runtime_info.input` pieces below. For every field, see the
<a href="/docs/blocks/tracer/advanced-usages/configuration">Configuration Guide</a>.

### LLM API Config

Tracer starts a per-job LiteLLM proxy in front of your model. Point `llm_api` at
the raw upstream endpoint:

<ConfigSnippet title="blocks/tracer/config.yaml">
{"runtime_info:\n  input:\n    llm_api:\n      api_key: <YOUR_API_KEY>\n      api_base_url: https://your-openai-compatible-endpoint/v1\n      model: openai/Qwen3.6-35B-A3B                  # upstream model called by the agent\n      protocols: [openai_compatible, anthropic_compatible]\n      served_via: per_job_litellm_proxy\n\n    litellm_proxy:\n      port: 4003                                     # local proxy port for this Tracer job\n      master_key: dummy-key-cf                       # functional dummy key for the proxy"}
</ConfigSnippet>

Never commit real API keys or private endpoints to `config.yaml`.

### Task Source Config

For the full LegoFlow path, Tracer reads Curator's merged verified tasks:

<ConfigSnippet title="blocks/tracer/config.yaml">
{"runtime_info:\n  input:\n    task_source:\n      provider: local                                # local Curator output\n      dataset_name: ../curator/artifacts/merged_swe_tasks # contains task dirs + verifiable_tasks.txt\n      split: train"}
</ConfigSnippet>

During `/tracer:run`, Tracer copies this source into its own
`artifacts/tasks/<dataset>/` area before Harbor starts. If
`verifiable_tasks.txt` exists, only those verified task IDs are staged.

In the full LegoFlow pipeline, this is the handoff from Curator:

```text
blocks/curator/artifacts/merged_swe_tasks
  -> blocks/tracer/artifacts/tasks/<dataset>
```

### Rollout Config

Start with a small task cap and modest concurrency:

<ConfigSnippet title="blocks/tracer/config.yaml">
{"runtime_info:\n  input:\n    harbor_job:\n      jobs_dir: artifacts/jobs              # Harbor jobs and trajectories land here\n      n_concurrent: 4                       # keep small for the first run\n      n_tasks: 10                           # null = all prepared tasks\n      max_retries: 2\n      timeout_multiplier: 5"}
</ConfigSnippet>

### Agent Config

Choose one scaffold and keep its runtime image, version, and conversion scaffold
aligned. The default Claude Code profile looks like this:

<ConfigSnippet title="blocks/tracer/config.yaml">
{"runtime_info:\n  input:\n    agent:\n      name: custom-claude-code              # custom-claude-code | custom-openhands-sdk | custom-opencode\n      version: 2.1.118\n      runtime_image: docker.io/jierun/c-cc-2.1.118:v0.1\n      runtime_host_path: artifacts/agent-runtime/claude-code\n      max_turns: 80\n      temperature: 0.7"}
</ConfigSnippet>

### SFT Conversion Config

If you want Trainer-ready LF data after rollout, enable conversion. Otherwise
leave it off and use raw trajectories only.

<ConfigSnippet title="blocks/tracer/config.yaml">
{"runtime_info:\n  input:\n    sft_conversion:\n      enabled: true                         # false = skip conversion after rollout\n      scaffold: auto                        # auto infers from agent.name\n      tokenizer_name: Qwen/Qwen3.5-35B-A3B-Base\n      out_dir: artifacts/sft_data\n      max_instances: null                   # null = convert all successful trajectories"}
</ConfigSnippet>

Now run setup:

```text
/tracer:setup
```

This prepares the pinned `repos/harbor` and `repos/swe_data_process` checkouts,
builds the Harbor/LiteLLM/conversion environments, and checks the local runtime
paths. Re-running it is fine.

## Check

Before launching containers or spending model tokens, run:

```text
/tracer:check
```

This is read-only. It checks config, repo pins, environments, task source,
model endpoint, proxy port, Docker, agent runtime, and conversion settings. For
exact pass conditions, see [Test Cases](/docs/blocks/tracer/test-cases). A healthy report
should leave you ready for task preparation and rollout.

Fix required failures before continuing.

## Run Trajectories

Launch the rollout job:

```text
/tracer:run
```

Tracer starts the per-job LiteLLM proxy, builds the Harbor command from
`config.yaml`, stages tasks under `artifacts/tasks/<dataset>/`, excludes
already processed or manually retired tasks, captures trajectories, optionally
converts SFT data, and archives the run.

Task preparation happens as part of the run path. For local Curator output,
Tracer trusts `verifiable_tasks.txt` when it exists and stages only verified
tasks. Hugging Face sources are downloaded and unpacked into the same
`artifacts/tasks/<dataset>/` layout. Tracer also skips tasks already recorded in
`artifacts/processed_tasks.yaml` or manually listed in `excluded_tasks.txt`, so
ordinary follow-up runs continue from the remaining work.

The main outputs are:

```text
artifacts/jobs/<job>/result.json
artifacts/jobs/<job>/<task>/agent/litellm-trajectory.jsonl
artifacts/sft_data/<job>/lf.json      # only when sft_conversion.enabled: true
```

For the artifact layout and handoff contract, see [Output Format](/docs/blocks/tracer/outputs).

## Trajectory Conversion

Raw rollout trajectories are useful for inspection, but Trainer usually needs
clean SFT data. If `sft_conversion.enabled: true`, Tracer converts successful
rollouts after `/tracer:run`. You can also ask `/tracer:dashboard` to refresh
conversion and stats for a finished job.

The conversion path has three layers:

| Layer | Format | Purpose |
| --- | --- | --- |
| **Raw trajectory** | Scaffold-specific Harbor/LiteLLM logs from Claude Code, OpenCode, OpenHands SDK, or Terminus-2. | Preserve the exact rollout trace for debugging and analysis. |
| **IM** | Intermediate JSONL with OpenAI-style messages and normalized `tool_calls`. | Give all scaffolds one shared trajectory schema for scoring and filtering. |
| **LF** | LLaMA-Factory ShareGPT JSON array. | The Trainer-ready SFT format; this is the usual downstream handoff. |

The converted files live under:

```text
artifacts/sft_data/<job>/
├── im.jsonl       # scored intermediate message records
├── lf.json        # Trainer-ready LLaMA-Factory / ShareGPT data
└── lf.stats.json  # token, turn, and score statistics for the dashboard
```

For the full conversion flow and supported scaffold keys, see
[Trajectory Conversion](/docs/blocks/tracer/advanced-usages/trajectory-conversion) and [Supported Scaffolds](/docs/blocks/tracer/advanced-usages/scaffolds).

## Hand Over to Trainer

For most training runs, hand over the converted LF file rather than raw
trajectories. After `/tracer:run`, choose the finished job directory under
`artifacts/sft_data/` and point Trainer to its `lf.json`:

<ConfigSnippet title="blocks/trainer/config.yaml">
{"runtime_info:\n  input:\n    source:\n      type: local_lf                              # use Tracer's converted LF file\n      lf_path: ../tracer/artifacts/sft_data/<job>/lf.json # replace <job> with the real Tracer job\n\n    conversion:\n      data_name: my_tracer_dataset                # dataset key registered in LLaMA-Factory\n      max_instances: 0                            # 0 = train on all examples in lf.json"}
</ConfigSnippet>

Use `source.type: local_lf` when Tracer already produced `lf.json`. Use
`harbor_job` only when you intentionally want Trainer to convert a raw Tracer
job itself.

## Dashboard Visualization

After a job starts or finishes, open the dashboard:

```text
/tracer:dashboard
```

The dashboard helps inspect job progress, per-task trajectories, rewards,
failure patterns, and converted SFT data. It reads `artifacts/` directly; if a
run is still active, keep watching the job log and `artifacts/jobs/<job>/` too.

For the internal rollout mechanism, see [Design](/docs/blocks/tracer/mechanism).
