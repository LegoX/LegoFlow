Introduction

Key ideas behind SWE-Lego-Live

Training a strong coding agent is not a single training job. A realistic SWE pipeline has to mine useful GitHub changes, turn them into verifiable tasks, roll agents out in isolated environments, filter and convert trajectories, train with SFT or RL, and evaluate the resulting model again. Each stage tends to grow its own scripts, storage layout, runtime assumptions, GPU requirements, and failure modes. The hard part is not only running the stages; it is keeping their handoffs reproducible as the data, repos, models, and infrastructure keep changing.

SWE-Lego-Live turns that loop into one agentic workflow. Instead of treating data construction, rollout, training, and evaluation as disconnected jobs, it keeps them in a live pipeline where each stage can be checked, rerun, inspected, and extended by agents.

What Can We Do with SWE-Lego-Live?

SWE-Lego-Live supports three core workflows:

  • Task generation — curate high-quality SWE tasks from real GitHub pull requests, with consistent rubrics for task quality and bi-weekly dataset updates that keep the task pool aligned with live repository activity.
  • Trajectory rollout — run multiple coding scaffolds, including Claude Code, OpenCode, OpenHands, and Terminus, to produce diverse SWE trajectories under a shared tracing and validation workflow.
  • Trajectory conversion, training, and evaluation — convert rollout traces into training-ready formats, launch end-to-end SFT or RL workflows, and evaluate checkpoints with dashboards that support inspection, comparison, and follow-up analysis.

Pipeline Roles

A block is a contract for agentic workflows and one runnable unit in the pipeline. Each block owns its config, scripts, plugin skills, artifacts, and dashboard, while exposing the same user-facing commands: /<block>:setup, /<block>:check, and /<block>:run. This means the full workflow can be started and inspected through plugin skills instead of hand-written orchestration scripts.

The diagram starts from objective tasks: generate SWE trajectory data, improve terminal-agent capability, and support longer end-to-end tasks. Those objectives enter the root block, which resolves the config tree, dispatches block runs, and archives run state.

Under the root block, the main stages are:

  • curator turns GitHub pull requests into verified SWE tasks.
  • tracer runs coding agents in isolated environments and records task trajectories.
  • trainer converts verified trajectories into SFT or RL training runs.
  • evaluator measures checkpoints on SWE benchmarks and reports model progress.

Why Blocks?

Blocks make the pipeline easier to use and easier to change. Because every stage follows the same contract, users can run the whole system through plugin skills, restart a failed stage from its archived state, swap one block without breaking the others, and inspect artifacts through a consistent dashboard interface.

This is especially useful for SWE workflows because different stages need different resources: curation may run locally, tracing may need containerized sandboxes, training may need remote GPUs, and evaluation may depend on model-serving endpoints. Blocks hide those operational differences behind the same setup-check-run lifecycle.

From SWE-Lego to SWE-Lego-Live

SWE-Lego-Live builds on our earlier project, SWE-Lego, which focused on constructing software-engineering data from real repository changes. The live version keeps that data-centric foundation, then adds an agent-operated pipeline around it: blocks for curation, rollout, training, and evaluation; dashboards for run state; and archives that preserve the exact configs, scripts, and repo SHAs behind each run.
