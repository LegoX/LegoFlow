This case study shows one AI agent operating LegoFlow across **Curator**,
**Tracer**, **Trainer**, and **Evaluator**. Starting from GitHub-derived tasks
plus imported Hugging Face/SWE-bench task instances, the run collected teacher
trajectories, trained
`Qwen3.5-35B-A3B-Base`, and evaluated the result on SWE-bench Verified.
Humans approved expensive or irreversible operations; the agent operated and
adapted the pipeline between those approval gates.

The run began with **zero external trajectories**. Its 4,166-task pool combined
3,518 tasks produced from GitHub with 648 imported Hugging Face/SWE-bench task
instances. The training trajectories were then collected through this
pipeline. The teacher model was `GLM-5.2`; Curator used
`claude-sonnet-4-6` through its Claude Code task-creation path.

<Callout title="Result, not a guarantee" type="warning">
The reported percentages belong to one completed experiment and its archived
conditions. Re-running a live GitHub and multi-agent pipeline can reproduce the
workflow and validate the same hypotheses, but it does not guarantee identical
tasks, trajectories, or benchmark scores. Read the
[reproducibility notes](/docs/showcase/reproducibility) before planning a run.
</Callout>

## The end-to-end result

```text
merged GitHub PRs
  -> Curator: 4,166 verifiable Python tasks
  -> Tracer: 915 solved teacher trajectories
  -> quality selection: 512 depth-filtered trajectories
  -> Trainer: full-parameter SFT, 128k context, 3 epochs
  -> Evaluator: 64.4% on SWE-bench Verified
```

| Stage | What happened | Recorded result |
| --- | --- | --- |
| **Curator** | Built a Python task pool from 3,518 GitHub-derived tasks plus 648 imported Hugging Face/SWE-bench tasks. | **4,166** tasks |
| **Tracer** | Asked `GLM-5.2` to solve tasks in isolated environments and archived the trajectories. | **915** solved trajectories |
| **Selection** | Removed duplicate and shallow trajectories, favoring reasoning substance over reasoning frequency. | **512** trajectories |
| **Trainer** | Full-parameter SFT of `Qwen3.5-35B-A3B-Base` at 128k context on 8× H800 80GB GPUs. | 3 epochs, 24 optimizer steps |
| **Evaluator** | Ran the trained model on SWE-bench Verified. | **64.4%** solve rate |

## What the agent changed between attempts

The first training attempt used 500 trajectories and reached **56.1%**. The
agent then inspected its own trajectories. A `<think>` block appeared in 80.7%
of model turns, but many blocks were only short transition phrases rather than
substantive debugging.

The second attempt changed the selection objective: keep trajectories whose
reasoning averaged at least 500 characters per turn, accepting lower coverage
in exchange for deeper reasoning. The final selection contained 512
trajectories. Median reasoning depth rose from 140 to **959 characters per
turn**, while reasoning coverage fell from 80.7% to 30.7%.

| Metric | First attempt | Second attempt | Change |
| --- | ---: | ---: | ---: |
| Trajectories | 500 | 512 | +2.4% |
| Reasoning coverage | 80.7% | 30.7% | -50 points |
| Reasoning depth | 140 char/block | 959 char/turn | Different denominators |
| Solve rate | 56.1% | **64.4%** | **+8.3 points** |

The teacher did not become stronger between attempts: both used `GLM-5.2`.
The 8.3-point gain is consistent with the reasoning-depth hypothesis, but the
two runs used different task pools and prompts, so the comparison does not
isolate filtering as the only cause. During conversion, the agent also found
tool calls that the evaluation harness could not parse and normalized them
before training.

## Training

The selected data was used for full-parameter SFT with a 128k-token context,
global batch size 64, learning rate `5e-5`, and three epochs. The run used 512
trajectories and completed 24 optimizer steps.

Two infrastructure corrections were required:

- Host memory was exhausted when `use_unsloth_gc` offloaded activations at the
  128k context length. The run switched to standard gradient checkpointing.
- NCCL selected `eth0` on a single multi-GPU host. Setting the communication
  interface to loopback (`lo`) restored distributed synchronization.

Step loss fell without divergence: 0.5236 at step 1, a minimum of 0.2294 at
step 23, and 0.2391 at step 24. The aggregate training loss was 0.3684—the
rounded 0.369 summary shown in the figure.

## Evaluation

The untrained base model scored **7.6%** on SWE-bench Verified. The
coverage-first attempt reached **56.1%**, and the depth-first attempt reached
**64.4% (322/500)** after the documented crash-and-unsolved retry protocol.
This was not a single deterministic pass. The result is 8.3 points above the
first SFT attempt and 56.8 points above the base model.

## Why LegoFlow makes this possible

Three design properties let the agent diagnose and improve a run that spans
multiple modules:

1. **Dependencies across blocks are declared, not implied.** Each block states
   which upstream outputs it consumes and which downstream inputs it feeds. A
   format mismatch can therefore be traced to the producing block, and
   preflight checks can reject broken wiring before an expensive job starts.
2. **Every run archives its execution evidence.** The automatic archive records
   status, timestamps, exit code, config and script snapshots, and vendored
   repository SHAs. Block outputs and logs remain in `artifacts/` and can be
   referenced or copied into the archive when needed. This gives the agent a
   durable scene to inspect after success or failure.
3. **Every block exposes the same lifecycle and archive shape.** Curator,
   Tracer, Trainer, and Evaluator can be operated through setup, check, run,
   archive, and dashboard surfaces. Metrics such as task verification,
   reasoning depth, training loss, and solve rate can be compared across block
   boundaries without coupling the root workflow to each implementation.

These properties do not make an LLM or an external service deterministic.
They make adaptations **visible, bounded by interfaces, and reviewable**. That
is why the agent could move traffic away from failing inference endpoints,
repair trajectory formatting, alter the data-selection rule, correct training
memory behavior, and rerun only the affected stages.
