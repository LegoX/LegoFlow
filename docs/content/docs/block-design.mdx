title: Block Design
description: Understand a block's files, configuration, and plugin skills

A block is the smallest self-contained unit in SWE-Lego-Live. Curator, Tracer,
Trainer, and Evaluator solve different problems, but they share the same
structure, configuration contract, and operational lifecycle. Once you
understand one block, the others should feel familiar.


## 1. Block Structure

The diagram below shows the block boundary and the information that moves
through it. Configuration and pinned repositories describe a reproducible run;
scripts perform the work; artifacts and dashboards make the result observable.

![Anatomy of a SWE-Lego-Live block](/figures/block-definition-editable.png)

A typical block uses the following layout. Some blocks add domain-specific
scripts or documentation, but each directory keeps the same responsibility.

```text
<block-name>/
├── .claude/
│   └── plugins/<block-name>-plugin/
│         ├── README.md               # Human-readable plugin documentation
│         ├── resources/              # Optional templates and reference material
│         └── skills/
│             ├── setup/SKILL.md      # Bootstrap the block
│             ├── check/SKILL.md      # Validate readiness without launching a run
│             ├── dashboard/SKILL.md  # Inspect progress and results
│             ├── run/SKILL.md        # Confirm and execute the block
│             └── ...
│
├── CLAUDE.md                         # Operating contract
├── config.yaml                       # Identity file to define the current block
│
├── repos/                            # Repositories associated with this block, added as git submodules
├── memory/                           # Durable notes, decisions, and operating context
├── scripts/                          # The associated running scripts used by the agent
├── dashboard/                        # Text or web views over logs, metrics, and artifacts
├── artifacts/                        # The output directories produced by this block
│   ├── index.yaml                    # The running record
│   └── archives/
│       └── run_NNN/                  # Frozen config, scripts, metadata, and optional logs
```


## 2. Configuration File Template

Every root block and subblock has a `config.yaml` with exactly two top-level
sections: `meta_info` and `runtime_info`. This file can fully characeterize the block, and we provide a  generic template as follows:

```yaml
meta_info:
  # Stable identity. name should match the block's directory name.
  name: example_block
  label: Example Block
  description: "One sentence describing the work this block owns."
  parent: swe_lego_live               # null for the root block

  # Parent blocks list direct children and their roles here.
  subblocks: {}

  # This block declares every data handoff in both directions. Keep both mappings, even when one or both are empty.
  dependencies:
    from: {}
    to: {}

  # Repositories used by this block are checked out under repos/ and pinned.
  repos: {}
    harbor:
      name: harbor
      commit_id: <full commit SHA>
      role: "Runs tasks in reproducible environments."

  # Host-local environment used by scripts in this block.
  environment:
    venv_name: example
    venv_path: artifacts/env/example
    requirements: requirements.txt
    description: "Python environment for this block."

  # local or null means the current machine. A real host means SSH and tmux.
  resources:
    ip: local
    directory: null                   # remote working directory when ip is remote
    description: "Where this block runs."
    public_storage: null              # optional shared output location

runtime_info:
  input:
    api_base_url: human               # required: replace before checking or running
    api_key: ""                       # supplied through an environment or ignored file
    optional_filter: null             # intentionally unset; use the default behavior
    ...

  output:
    result_dir:
      description: "Directory containing this block's results."
      path: artifacts/results         # static, block-relative output
    selected_checkpoint:
      description: "Checkpoint chosen after training."
      value: null                     # written by the run script when known
    ...
```

### How to fill the template

Start with `runtime_info.input`. The marker tells you whether a field needs
attention:

| Value | What it means | What you should do |
| --- | --- | --- |
| `human` | A required decision or external value | Replace it before running; validation fails while it remains |
| `""` | Supplied automatically, through an environment variable, or through a local file | Leave it empty and follow the field's comment or block setup guide |
| `null` | Intentionally unset, default, or all | Leave it unless you want to opt into another behavior |
| Any other value | A real working default | Keep it unless your run needs a different value |

Do not place secrets in committed configuration. API keys, GitHub tokens, and
similar credentials should use the environment variables or ignored local
files named by the owning block's setup guide.

Leave `runtime_info.output` alone before a run. A static `path` is part of the
block contract; a run-produced `value` starts as `null` and is written by the
block's scripts after the output exists.


## 3. Plugin Skills

A block plugin turns the directory contract into a consistent set of Claude
Code commands. The namespace is always the block name, and the verb describes
one clear lifecycle action:

```text
/<block-name>:<action>
```

For example, Tracer exposes `/tracer:setup`, `/tracer:check`,
`/tracer:dashboard`, and `/tracer:run`. The directory and manifest follow the
same identity: `tracer-plugin` and `name: tracer`.

### Shared lifecycle skills

| Command pattern | Purpose | Changes run state? |
| --- | --- | --- |
| `/<block>:setup` | Install or verify tools, sync pinned repositories, build environments, and help fill missing external inputs. It is idempotent and should bring the block to the point where its check can pass. | May update setup files and environments, but never launches the workload |
| `/<block>:check` | Run read-only preflight checks for configuration, dependencies, repositories, credentials, endpoints, Docker, GPUs, and the block's dry run. It is mandatory before a run. | No |
| `/<block>:dashboard` | Summarize the latest state, metrics, logs, and artifacts; optionally start the block's web dashboard. | No |
| `/<block>:run` | Repeat preflight, show the run configuration, wait for explicit confirmation, and execute. A leaf invokes its own start script; a parent dispatches child run skills in dependency order. | Yes |

The root plugin follows the same lifecycle and adds `/root:create`, which
scaffolds a new block from the canonical structure and registers it with its
parent. Creation is a root responsibility, so leaf plugins do not expose this
command.

### Naming principles

- Use the block name as the namespace: `/curator:...`, `/tracer:...`,
  `/trainer:...`, and `/evaluator:...`. This makes ownership immediately clear.
- Keep the four lifecycle verbs consistent across blocks. A user who knows how
  to check one block should know how to check any block.
- Give a domain-specific operation a concrete, action-oriented name only when
  it represents a meaningful workflow of its own. Curator therefore exposes
  `/curator:collect-prs` and `/curator:create-tasks`; its `/curator:run`
  remains the common lifecycle entry point and delegates to the appropriate
  workflow.
- Use lowercase kebab-case for multiword actions, and keep the skill directory
  name identical to the command action, such as `collect-prs/SKILL.md`.
- Put confirmation and interpretation in the skill, but keep deterministic
  execution in `scripts/`. This separation makes the command approachable
  without hiding the reproducible shell entry points.

This shared naming is an interface, not a claim that every block does the same
work. Each skill still owns the checks and safeguards that matter to its block:
Curator verifies task creation, Tracer checks rollout infrastructure, Trainer
checks GPUs and checkpoint safety, and Evaluator checks its benchmark and
model endpoint.
