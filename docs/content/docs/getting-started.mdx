SWE-Lego-Live turns real software changes into training data, a fine-tuned
model, and an evaluation report. The standard workflow has four stages:

```text
1. SWE task curation (Curator)
   -> 2. Trajectory generation (Tracer)
   -> 3. Supervised fine-tuning (Trainer)
   -> 4. Model evaluation (Evaluator)
```

You can operate the blocks one at a time or coordinate the complete block tree
from the repository root. If this is your first run, use the block-by-block
workflow: it makes every handoff visible and is the clearest way to learn the
system.


## Before you start

You will need:

- **Claude Code** with this repository's plugins enabled.
- **Docker** on the hosts that run Curator, Tracer, and Evaluator.
- An **OpenAI-compatible or Anthropic-compatible LLM endpoint** for task
  curation, trajectory generation, and evaluation.
- **GitHub token(s)** with repository read access for Curator.
- A **GPU node**, typically with 8 A100/H100-class GPUs, for full-parameter
  SFT. A local model evaluated through vLLM also needs GPU capacity.
- Git, Python, and [uv](https://docs.astral.sh/uv/) on the relevant hosts.

Clone the project and its pinned submodules:

```bash
git clone --recurse-submodules git@github.com:SWE-Lego/SWE-Lego-Live.git
cd SWE-Lego-Live
```

If you already cloned without submodules, run:

```bash
git submodule update --init --recursive
```


## Mode 1: Run one block at a time

This is the recommended way to learn the complete pipeline. Each block owns
its environment, configuration, checks, execution logic, and artifacts. The
broad rhythm is always **setup -> check -> confirm -> run**, but the exact
inputs and launch behavior are block-specific. Follow the linked Getting
Started page instead of configuring a block from this overview.

### 1. Curator: build verified SWE tasks

Curator collects real GitHub pull requests, converts suitable changes into
containerized SWE tasks, and validates each task with NOP and Oracle checks.
Only task IDs written to `verifiable_tasks.txt` are safe for downstream use.

[Set up and run Curator](/docs/sub-block/curator/getting-started)

### 2. Tracer: generate agent trajectories

Tracer consumes verified tasks, runs a selected coding-agent scaffold through
Harbor, and records each rollout as a replayable LiteLLM trajectory. It can
also convert successful trajectories into LLaMA-Factory-ready SFT data.

[Set up and run Tracer](/docs/sub-block/tracer/getting-started)

### 3. Trainer: perform supervised fine-tuning

Trainer accepts a Harbor job, a prepared Hugging Face dataset, or a local
LF/ShareGPT file. It registers the dataset, launches LLaMA-Factory with
DeepSpeed, and records the resulting checkpoint and training metrics.

[Set up and run Trainer](/docs/sub-block/trainer/getting-started)

### 4. Evaluator: measure a configured model

Evaluator runs a benchmark from Harbor's registry against either a remote API
or a local checkpoint served with vLLM. It stores verifier results,
trajectories, and post-run analysis for the dashboard.

[Set up and run Evaluator](/docs/sub-block/evaluator/getting-started)

<Callout title="Why the detailed steps live with each block" type="info">
The skills are intentionally not identical under the hood. Curator separates
PR collection from task creation, Trainer performs live GPU and
checkpoint-safety checks, and Evaluator probes the model endpoint before
launch. Keeping those instructions with their owning block prevents this page
from becoming a second, stale copy of the runtime contract.
</Callout>


## Mode 2: Coordinate from the repository root

Root mode gives you one entry point for the complete tree. The root is a
coordinator: its own `config.yaml` describes the project and lists the
participating blocks, while every external value remains in the block that
uses it. The root does not collect shared API keys or duplicate child settings.

### Step 1: Set up the root configuration

From the repository root, run:

```text
/root:setup
```

This verifies shared tooling and ensures the root `config.yaml` contains the
project identity, a role-only `meta_info.subblocks` roster, empty root
dependencies, and empty root runtime inputs and outputs. It can then offer to
invoke each child's setup skill. Accept the blocks you intend to prepare; each
child setup owns its repositories, environment, credentials, and external
inputs.

A minimal root configuration looks like this:

```yaml
meta_info:
  name: swe_lego_live
  parent: null
  subblocks:
    curator: {role: "Build verified SWE tasks"}
    tracer: {role: "Generate trajectories from verified tasks"}
    trainer: {role: "Train a model on selected trajectories"}
    evaluator: {role: "Evaluate a configured model on a benchmark"}
  dependencies: {from: {}, to: {}}
  resources:
    ip: local

runtime_info:
  input: {}
  output: {}
```

Do not add dependency wiring to the root roster. Each consumer declares its
upstream handoffs under its own `meta_info.dependencies.from`, and each producer
declares the matching `meta_info.dependencies.to`. The root reads those edges
to determine execution order.

Keep secrets in environment variables or ignored credential files. The
block-specific Getting Started pages explain exactly which values each setup
expects:

- [Curator setup](/docs/sub-block/curator/getting-started)
- [Tracer setup](/docs/sub-block/tracer/getting-started)
- [Trainer setup](/docs/sub-block/trainer/getting-started)
- [Evaluator setup](/docs/sub-block/evaluator/getting-started)

### Step 2: Validate the tree

First validate the configuration schema and cross-block wiring:

```bash
python3 scripts/validate_config.py --root .
```

Then ask the root plugin to perform the full preflight:

```text
/root:check
```

The check is read-only. It walks the declared tree and reports unfilled inputs,
dependency mismatches, repository-pin drift, missing environments, host
reachability, credentials, live endpoints, and each block's dry-run findings.
Fix every failure and review the configuration summary before continuing.

To inspect only one block while staying at the root, name it explicitly:

```text
/root:check trainer
```

### Step 3: Confirm and run

After the full check passes, review the proposed launch and confirm it
explicitly. Then run:

```text
/root:run
```

For a parent block, the root plugin sorts children from their declared
dependencies and calls each child's own run skill in order. It waits for a
child to finish before starting its downstream consumers, and stops the
pipeline if a child fails or you decline a confirmation. Each leaf skill owns
its preflight, remote-execution decision, `scripts/start.sh`, and archive.

You can also select one child from the repository root:

```text
/root:run trainer
```

<Callout title="Evaluator model selection" type="info">
Evaluator is currently an independent leaf in the dependency graph. Running
it after Trainer does not automatically point it at Trainer's newest
checkpoint. Configure Evaluator's remote endpoint or local model path in its
own setup before launching it.
</Callout>

For block-specific modes, configuration changes, monitoring, or recovery, use
the owning block's Getting Started page. Root orchestration deliberately keeps
those details with the block that understands them.


## Follow the outputs

Every leaf block records its own history. The newest entry in
`artifacts/index.yaml` is the latest recorded terminal state, while
`artifacts/archives/run_NNN/` preserves the configuration, scripts, metadata,
and optional run logs for that execution.

Use the block's dashboard when you want a live view of progress and results.
