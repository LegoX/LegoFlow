LegoFlow is a tree of blocks. Each block owns its configuration, runtime,
artifacts, and operating plugin; the root plugin coordinates the tree.

## Recommended: operate via the Claude plugin

Launch Claude Code from the repository root so the root, curator, tracer,
trainer, and evaluator plugins in `.claude/settings.json` all load. The normal
lifecycle is:

```text
/root:setup             # bootstrap shared tooling and optionally set up each block
/root:check             # preflight the whole tree
/root:check tracer      # preflight one block
/root:run tracer        # run one block after check + explicit confirmation
/root:dashboard         # open the tree-wide status dashboard
```

Each block also exposes its own operating commands. For example:

```text
/curator:collect-prs
/curator:create-tasks
/tracer:setup
/tracer:check
/tracer:run
/tracer:dashboard
```

Use `/root:run <block>` as the root-level orchestration entry point, or use the
block's own `/<block>:run` when you are already operating inside that block.
Do not invoke both for the same run. Both paths require a successful preflight
and an explicit confirmation before an expensive job starts.

`/root:create` is separate from the normal lifecycle: it scaffolds a new block
and is not needed to run the existing pipeline.

The commands read the checked-in `config.yaml` files. Edit configuration, not
the skill files or launch scripts. The rest of this page documents the
underlying setup and contracts for manual operation and debugging.

## Prerequisites

- **Claude Code** for the recommended plugin workflow.
- **Python 3 with PyYAML** and **uv** for config validation and block
  environments.
- **Docker** on the hosts that run curator, tracer, and evaluator.
- An **OpenAI-compatible LLM endpoint** for curator, tracer, and evaluator.
- **GitHub token(s)** for curator PR collection.
- An **8-GPU node** for the trainer's default distributed configuration.

Cloudflare Pages and authenticated Docker registry credentials are optional.
They can be configured through `/root:setup`; they improve dashboard publishing
and image-pull reliability but do not define pipeline inputs.

## 1. Clone the block tree

```bash
git clone --recurse-submodules <repo-url> LegoFlow
cd LegoFlow
```

If the repository was cloned without submodules:

```bash
git submodule update --init --recursive
```

## 2. Fill the block configs

Every block has a `config.yaml` with exactly two top-level sections:

- `meta_info` — identity, pinned repositories, execution resources, and
  dependency wiring.
- `runtime_info.input` / `runtime_info.output` — external inputs and declared
  outputs.

Live run state is not stored in `config.yaml`. Completed, failed, and
interrupted runs are recorded under `artifacts/index.yaml` and
`artifacts/archives/`.

### Fill rules

| Marker | Meaning |
| --- | --- |
| `human` | Must be replaced before the block can pass validation. |
| `""` | Supplied through an environment/file channel, auto-derived, or intentionally disabled; follow the inline comment. |
| `null` | Semantic unset/default/all; leave it unless selecting a non-default behavior. |
| anything else | A working value or default. |

Never commit real API keys or tokens. Prefer the environment or the ignored
local credential files named by each block.

### Current required inputs

| Block | Must fill | Environment or file inputs | Common adjustments |
| --- | --- | --- | --- |
| **curator** | `llm_api.api_key`, `llm_api.api_base_url` | `GITHUB_TOKENS` / `GITHUB_TOKEN` / ignored token file | provider mode, PR/task models, collection scale |
| **tracer** | `llm_api.api_key`, `llm_api.api_base_url` | HF token only for gated Hugging Face task sources | model, task source, concurrency/task cap, agent preset |
| **trainer** | none in the checked-in default | `WANDB_API_KEY`; `HF_TOKEN` for private datasets | source type, model, output directory, training parameters |
| **evaluator** | `llm_api.api_key`, `llm_api.api_base_url` | preset-specific credentials, if any | remote API vs local vLLM, benchmark, agent preset |

The root's `runtime_info.input.cloudflare` and `runtime_info.input.docker` are
optional shared infrastructure settings. Keep secret fields empty in the
tracked file and provide tokens/passwords through environment variables.

### Dependencies between blocks

Each edge is declared twice: the consumer's `dependencies.from` and the
producer's matching `dependencies.to`. The validator checks both ends.

The current curator-to-tracer handoff is:

```yaml
# blocks/tracer/config.yaml
meta_info:
  dependencies:
    from:
      task_source.dataset_name:
        from: curator.output.merged_tasks_dir
        when: {task_source.provider: local}
```

```yaml
# blocks/curator/config.yaml
meta_info:
  dependencies:
    to:
      merged_tasks_dir:
        to: tracer.input.task_source.dataset_name
        when: {tracer.input.task_source.provider: local}
```

Tracer's raw trajectories feed the trainer when the trainer selects a Harbor
job source:

```yaml
# blocks/tracer/config.yaml
meta_info:
  dependencies:
    to:
      raw_trajectories_dir:
        to: trainer.input.source.job_dir
        when: {trainer.input.source.type: harbor_job}
```

Do not edit dependency wiring merely to satisfy a check. It is the pipeline's
handoff contract.

## 3. Validate before running

Run the shared schema and dependency validator:

```bash
python3 scripts/validate_config.py --root .
python3 scripts/validate_config.py --block blocks/tracer
```

Then use `/root:check` or the block's `:<block>:check` command. Block checks add
live probes for endpoints, repos, Docker, GPUs, task sources, and environments
that the static validator cannot verify.

## 4. Run and inspect results

After the relevant check passes and you confirm the reported configuration:

```text
/root:run tracer
```

Leaf blocks execute their own `scripts/start.sh`. The script's EXIT trap
archives the run under:

```text
artifacts/archives/run_NNN/
├── metadata.yaml
├── config.yaml
└── scripts/
```

and appends an entry to `artifacts/index.yaml`. Job-specific results remain
under the block's declared output directories, such as
`blocks/tracer/artifacts/jobs/`.

Use `/root:dashboard` for a tree-wide view or the block dashboard for detailed
metrics:

```text
/tracer:dashboard
```

See the corresponding page under [Blocks](/docs/blocks/curator) for each
block's exact setup, run modes, outputs, and recovery procedures.
