## Prerequisites

- A **CPU** node with enough disk quota (e.g., >= 10T) for `curator` and `tracer` to create SWE tasks and trajectories
- A **GPU** node (preferrably 8 GPU cards) for `trainer` and `evaluator` to train and evaluate customized models
- A LLM API key used to either curate SWE tasks, generate trajectory rollouts etc.
- **GitHub token(s)** with `repo` read scope, for PR collection in `curator`.
- **Claude Code** or **Codex** (coming soon)


## Step 1: Clone

```bash
git clone --recurse-submodules <repo-url> SWE-Lego-Live
cd SWE-Lego-Live
```
If you cloned without `--recurse-submodules`, run `git submodule update --init --recursive`.


## Step 2: Fill in `config.yaml`

Every block is driven by a `config.yaml`. The file declares what the block is, where it runs, which repositories and child blocks it depends on, what values a user must provide, and what outputs the block will publish after a run.

The schema has three main parts:

- `meta_info` describes the block identity, pinned repositories, execution environment, resources, and subblock wiring.
- `runtime_info.input` contains values that come from outside the block tree, such as API keys, model names, GitHub tokens, dataset paths, or human choices.
- `runtime_info.output` contains values produced by the block, such as verified task directories, trajectory directories, checkpoint paths, or evaluator reports.

For example, a root block can wire `curator` into `tracer` by declaring that `tracer` receives its tasks from `curator.output.verified_tasks_dir`, while values like API keys are still marked as `human`:

```yaml
meta_info:
  name: root
  subblocks:
    curator:
      role: generate verified SWE tasks
      dependencies:
        github_tokens: human
        llm_api: human
    tracer:
      role: roll out agent trajectories
      dependencies:
        task_source: curator.output.verified_tasks_dir
        llm_api: human

runtime_info:
  input:
    github_tokens: "ghp_xxx,ghp_yyy"
    llm_api:
      api_base_url: "https://api.example.com/v1"
      api_key: "sk-..."
      model: "gpt-4.1"
  output: {}
```

When filling a block config, start with all `human` dependencies and all non-null `runtime_info.input` fields. Leave `runtime_info.output` empty before the first run; block scripts fill it after successful execution. Then run `/<block>:check` to catch missing tokens, unresolved dependencies, missing repos, or unreachable remote resources before launching a long job.


## Step 3: Running with Plugin Skills

Every block in SWE-Lego-Live is operated through the same plugin skills:

| Skill | What it does |
| --- | --- |
| `/<block>:setup` | Install dependencies, build environments, and fill default config values |
| `/<block>:check` | Validate config, inputs, environments, dependencies, repos, and live endpoints |
| `/<block>:run` | Execute the block end-to-end and archive the run |

Replace `<block>` with the block name — for example, `curator`, `tracer`, `trainer`, or `evaluator`. Same three verbs, every block.

### Step 3.1: `/<block>:setup` — install dependencies

Run setup once for the block you want to operate:

```text
/curator:setup        # clone repos, build envs, prepare default config
```

Each `:setup` is idempotent and safe to re-run — it only fills in fields that aren't already set, and only builds environments that don't already exist. After setup, the block's `config.yaml` will still have a handful of `runtime_info.input` fields that only you can provide (API keys, GitHub tokens, model names). Fill those by hand.

### Step 3.2: `/<block>:check` — preflight

`<block>:check` is read-only. It validates the schema, every filled input, every inter-block dependency, repo pins, environment paths, and live LLM endpoints (via a no-cost `GET /models` probe). It never modifies anything and never costs anything.

```text
/tracer:check         # validate tracer config, dependencies, Docker, and endpoints
```

Run `:check` after every config edit. It tells you exactly which input is unfilled, which submodule is missing, and whether the remote node is reachable, so you can fix gaps before committing to a long run.

### Step 3.3: `/<block>:run` — execute

Only run after the matching `:check` passes:

```text
/trainer:run          # convert trajectories and train
```

Each `:run` executes the block's `scripts/start.sh`. Long-running operations (multi-hour GPU training, multi-container rollouts) launch in tmux so they survive disconnects. Every run is archived automatically — `start.sh` installs an EXIT trap that fires `archive_run.sh` regardless of how the run exits (success, error, SIGINT, SIGTERM). One entry lands in `artifacts/index.yaml`, and the snapshot lives in `artifacts/archives/run_NNN/`.


## Working with Root

`/root:check` and `/root:run` recursively apply the same lifecycle across the whole tree, with a free-form argument that selects the target block:

```text
/root:check                         # check root + every subblock
/root:check curator                  # one block at a time
/root:run tracer                   # equivalent to /tracer:run
/root:run start the data pipeline   # paraphrased; resolves to the root orchestrator
```

An [Example Usage](/docs/example-usages) of root can be found here.

## Result Collection

The block's own artifacts are the source of truth:

- `artifacts/index.yaml` — newest entry's `status` (`completed | failed | interrupted`)
- `artifacts/archives/run_NNN/metadata.yaml` — id, timestamps, exit code, repo SHAs
- `artifacts/archives/run_NNN/config.yaml` — the frozen config that produced this run

Optionally, open the block dashboard for a visual summary:

```text
/tracer:dashboard     # inspect trajectory rollouts and conversion status
```

Dashboards expose the same run state, logs, metrics, and artifacts in a more readable view. See each block's own docs under [Blocks](/docs/sub-block/curator).
